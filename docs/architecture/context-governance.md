# Canonical context governance

Reusable instructions remain Agent Hub DB prompts. Memory remains citable knowledge with stable UUIDs; longer explanatory knowledge belongs in the Vault. This change does not introduce another policy store in a client or project file.

The Security Research policy was stored as a global prompt, while its project restriction existed only in prose. The old UI edited boot eligibility separately from the selector that loaded enabled globals. Migration `c7e92a160a31` gives it project scope `security-research` and explicit workflow activation of the same name; it is no longer global. Other existing globals and project placements are migrated without rewriting their contents. Migration `d8a30ef164b2` normalizes legacy project/agent scope encodings and indexes retained source evidence. Seed export preserves this metadata, and seeding remains insert-only.

## One selector and one renderer

`context_policy.py` interprets prompt policy and existing memory scope, applicability, triggers, tier and format. Memory disclosure metadata adds only activation and workflow names. Scope can be global, project, agent, or unassigned for a prompt. A matching explicit workflow can supplement scope; it cannot bypass consumer exclusions. Required applicable rules stay full and upfront or explicitly triggered. Advisory material can be relevant, conditional, or indexed for on-demand retrieval. Explicit retrieval returns the full body and preserves scope checks.

`runtime_context.py` owns final delivery for native clients, MCP, internal agents and the UI. Source eligibility precedes placement. Includes cannot make an unrelated or disabled source eligible. Agent ownership is separate and remains in the agent prompt stack. Computed tool guidance remains owned by its registry. No model is asked to decide authorization or required-rule inclusion.

Draft preview runs the exact assembler inside a rolled-back database savepoint. Save locks the placement layer and then source rows in stable order, checks source/placement revisions, applies the batch atomically, and records before/after snapshots. Undo is a new revision and rejects intervening edits. Memory edits preserve UUID, attribution and usage counts. Context records are separate from prompt/memory content and retain immutable review, change and feedback evidence.

## Operator workflow

Open Runtime Context, select the project, consumer and profile to inspect, then select a source name. Those selectors affect the preview. The inspector changes durable source scope, disclosure, format and targeting; include/exclude controls affect only the displayed project/profile. Owned and computed sources are visible but edited through their owners.

Stage one or several edits, inspect the exact before/after delivery and token delta, and save. Stale writes retain the draft for review. History includes batch undo and evidence. Dangling or ineffective placements are identified and can be staged for removal. Reference-selection policy remains available separately. Archive, disable, exclude here and on-demand disclosure are distinct operations.

Use the Why view to inspect a block or preview an advisory source's full retrieval. Explicit workflow activation can be saved for a known session/surface. It applies on the next supported context generation. It cannot retract messages already saved in a native thread; resume/fork remains the client's saved-context behavior.

## Reviews and honest evidence

Deterministic checks run without model calls. Interactive semantic reviews offer a candidate/cost preview and produce proposals. The existing curator schedule also processes changed evidence; Jev remains explicitly selected. Explicitly selected pairs are compared even without shared words. Unselected library and background neighborhood discovery use lexical overlap and can miss indirect contradictions; neither is advertised as exhaustive. Applicable agent-owned prompts and supplied visible native snapshots can be compared. Hidden native/provider instructions remain unobservable.

Review evidence retains exact passages and source revisions. Proposed edits enter the same staged workflow; their evidence is checked again under locks before save. Scheduled reviews store proposals. A separate recovery step can apply a clear authorized correction through the canonical action service, with exact supporting passages, revision checks, generated-delivery verification and retained undo. Unchanged reviewed versions are not repeatedly scheduled merely because no source mutation occurred.

Jev is a typed-judgment catalog entry, not a conversational/tool-running model. Its durable cache keys semantic content, effective short forms, scope, relevant consumer/task context, rubric and exact model version. Display names, counters, ordering of sets and source revision labels do not cause paid reclassification. Atomic reservation deduplicates concurrent dispatches; uncertain dispatches are retained and not automatically retried. Estimates and observed usage-priced costs are distinct from vendor billing. See [evaluation evidence](../evaluations/context-review/README.md).

User ratings, agent assessments, citations, generated context, bindings, observed delivery, retrieval and saved native context are separate signals. Legacy citation extraction remains supported, but citation no longer increments helpfulness. Automatic memory ratings retain their assessor/evidence and do not masquerade as owner feedback. Old utility counts are explicitly labelled as legacy mixed signals.

## Verification boundaries

Unit and UI tests cover scope, explicit workflows, exclusions, on-demand index/full retrieval, stale edits, preview rollback, cache identity, proposals and preserved draft state. A PostgreSQL integration test uses a disposable transactional schema inside `agent_hub_test` to verify real atomic save, rollback, undo and memory identity. Managed rebuilds apply migrations and seed the typed catalog entry. Live browser checks exercise project selection, source inspection, staged scope preview and discard; generation is checked through canonical CLI delivery. The native evaluation measures actual read-only task execution, with its limitations retained rather than inferred away.

## Proactive maintenance

Migration `e9b41fc275c3` adds one revision-bound work queue, ingestion deduplication and explicit per-session attention receipts. Prompt and memory revision writers, canonical changes, actionable feedback and review results feed it. Source revisions, not time-to-live guesses, invalidate evidence. Source changes supersede prior work without deleting history. Derived-count drift and proven dangling placements are repaired deterministically through canonical verification; failure is retained for investigation rather than retried every run.

The existing Memory Curator schedule owns incremental semantic work, sharing its configured batch allowance with rolling memory review. Co-applicable items share review requests and compare with neighbors. A database advisory transaction lock spans worker calls; durable claims survive provider waits. A later worker can identify an interrupted predecessor by acquiring that same lock, then hands off its uncertain work instead of blindly calling the provider again. Known completed/failed native sessions release their claims; unknown abandoned sessions require explicit recovery. No new cadence, spending budget or claim expiry is invented.

Routine background work, including queued semantic follow-up, adds no startup text. Canonical delivery emits a compact notice for blocked technical work in Agent Hub, unreported relevant owner decisions, or that session's own unfinished claim. The curator can see its entire relevant queue. Preview is read-only and cannot consume attention. Explicit acknowledgment records the inspected item version; claims and answers change the version. Listing work hides background items by default and retrieves the DB-owned maintenance guidance on demand. CLI, MCP, the existing internal `review_memory_system` tool and the dashboard use the same service and request schema.

Agents claim work, inspect current evidence, and can apply clear authorized corrections or resolve an existing canonical change receipt. Edits check source revisions and actual generation before closing, retaining undo history. Semantic findings alone are not edit authority. Only genuinely missing owner decisions become questions with recommendations; reporting a question requires an actual conversation anchor, and an answer retains its origin. No external message or notification is sent automatically. The Runtime Context activity panel is visibility and a fallback control, not a required owner review inbox.

The maintenance guide is a workflow-scoped DB prompt, retrieved on explicit use and absent from routine startup. Existing native threads retain their already-saved context; the next supported generation or retrieval can disclose updated maintenance state. Agent acknowledgments, generated context, and provider/model receipt remain distinct. See [Jev research and measurement limits](../evaluations/context-review/jev-maintenance-research.md).

The scheduled curator also owns follow-up. An unchanged failed or interrupted inference is retained without another provider call. Reviewer configuration, exact evidence and completed repair receipts identify genuinely changed attempts. Regular memory reviews reserve their attempt before inference and preserve rejected output in canonical history. A later failure after a resolved review reopens the incident without erasing its earlier resolution.

Concrete technical defects use SummitFlow's existing idempotent autonomous task intake. An uncertain acknowledgment replays the same frozen request. Task completion permits revalidation; it does not resolve the finding by itself. Failed revalidation stays visible and cannot repeatedly buy identical inference. Failed tasks are observed again so a resumed task can recover. Routine task-owned work stays out of other projects' startup context; blocked Agent Hub repairs and genuine owner decisions remain available to relevant agents.

A repair to canonical context can produce a durable database change without a Git diff. The maintenance work verifier checks the exact task/request identity, recurrence generation, immutable resolution event, current source revisions and canonical delivery. It returns a compact receipt without source contents or model calls. SummitFlow accepts that receipt as external work only when it can also establish that the task did not change the checkout. Code changes retain their normal quality and publication checks. Missing, stale or mismatched evidence remains unverified; a model's completion statement is never the receipt.

Task execution still follows the existing project permission and SummitFlow pickup guards. A queued task is not an execution receipt. Disabled automatic execution is surfaced as blocked; maintenance never flips the project-wide permission or uses a manual-dispatch path to bypass it. Routine canonical memory corrections use the scheduled curator and do not require this code-execution permission.

The operator can separately permit project execution and select which tasks the existing SummitFlow pickup schedule may run. Context maintenance identifies its tasks with `external_origin=agent-hub-context-maintenance`; this is a selection attribute, not new authority. SummitFlow's existing Task Filtering settings expose an optional `external_origins` allowlist, enforced both during pickup and autonomous dispatch. Production Agent Hub allows this origin only, retaining its existing one-task concurrency. General refactor discovery and persona heartbeats are independent schedules and remain disabled. Enabling maintenance must not implicitly enable them.

The production curator uses `codex/gpt-5.6-luna` at low reasoning through the owner's existing Codex/ChatGPT subscription, with no automatic fallback chain. The [September 2026 qualification](../evaluations/context-review/gemini-3.8-flash-maintenance-qualification.md) compares frozen synthetic regular-review and recovery cases. Luna preserved the required-rule delivery boundary; Gemini 3.8 Flash low proposed premature archival, while medium calls were unavailable across both configured accounts. This is bounded evidence, not a general model ranking. Gemini's existing healthy-account round-robin pool remains available for suitable workloads; curator failures retain their evidence for canonical recovery rather than silently selecting an unqualified route. Worker startup loads the DB catalog so scheduled calls use the same model capabilities as the API.

The old tier-optimizer and memory-cleanup schedules overlap this ownership: they can demote based on usage counts, consolidate from embedding similarity, or clear archived content based on age without the canonical evidence/change/undo path. Their production schedules were disabled on 2026-09-19 when maintenance was consolidated. Their code remains available for separately reviewed migration; no stored memories were deleted. Mechanical governance checks, session cleanup, telemetry retention and catalog refresh remain separate model-free jobs.

The daily curator uses its catalog route and existing shared allowance of ten work items, with a 45-day cadence for rolling memory review. That allowance is not a token ceiling or provider-call ceiling: batching, follow-up findings and configured fallbacks affect usage. Empty queues need no inference. Reviewer usage must be persisted through canonical completion tracking, including unsuccessful fallback attempts; unavailable historical usage stays unknown rather than being backfilled from text estimates. Jev is not a routine prerequisite.

The UI and agent status tool share outcome-based health: active failures, blocked repairs, owner decisions, latest successful review and the existing schedule. A completed worker invocation is not evidence of a healthy memory system. Revision-bound usage feedback records concrete observed mistakes, omissions and conflicts; non-use alone does not justify removing context. Jev remains optional until representative independent evidence supports making it a default.
