# Jev in development workflows — bounded local evaluation

**Finding (2026-09-23): do not add Jev to a development decision path yet.** No fresh Jev judgment was authorized for this cross-project evaluation: the only cumulative spending ledger is explicitly the Neri security-research pilot, while the separate context-screening caller has no cumulative cap. I ran live read-only workflow baselines, an authenticated zero-cost dry run, local cache probes, mocked failure probes, and independent downstream reviews. These establish several useful gaps and several places where existing tools already work. They do **not** establish a Jev-caused improvement in completed work.

The finite initial and untouched validation cases were registered in [cases-v1.json](cases-v1.json) before the probes. [results-v1.json](results-v1.json) holds the compact outcomes, types of evidence, unknowns, and measurements. The main input-quality failure is concrete. [The dry-run fixture](unverified-request-fixture.json) submitted a nonexistent authoritative source ID, an all-`a` content hash, and a worker-authored rubric with an all-`b` hash. The live endpoint returned [`status: dry_run`](unverified-request-dry-run.json), with no provider call or charge. The schema checks shape, but the endpoint does not assemble original requirements or verify these hashes against authoritative content. Eight older development-themed Jev dispatches record 8,545 input tokens and $0.000358890 in local accounting, plus answers and provenance hashes; they do not retain the original state/questions needed to grade those verdicts independently. The Neri-named pilot ledger also contains 108 SlopMiner-labeled dispatches; historical use does not authorize this evaluation to reuse it. Persuasive narration, leading “easy task” summaries, prompt injection in source text, candidate order effects on Jev, and genuine evidence changes therefore remain **untested Jev behaviors**, not passes.

The narrower existing context-screening cache did behave as intended under local perturbations: pair order and cosmetic identity left its key unchanged; evidence, candidate, context, rubric and model changes invalidated it. [Local results](local-probe-results.json) also retain search coverage and simple/exact repeat comparisons. [Mocked transport probes](transport-results.json) returned “not evaluated” after one timeout, unavailable-model response, or malformed response. The relevant existing Agent Hub tests passed (`st check pytest -- backend/tests/services/test_typesafe_jev.py backend/tests/services/test_context_governance.py`: **37 passed**). This mock does not prove a bounded live timeout: `call_typesafe_jev` creates its default HTTP client with `timeout=None`, and `screen_pairs` calls it without the Neri reservation ledger. The pilot dispatcher does reserve, deduplicate, account for uncertain billing, and refrain from retrying; its September ledger showed 240 succeeded dispatches, two uncertain reservations, $0.071314950 spent and $0.005376 reserved under the Neri-only $5 ceiling. These are local ledger amounts, not provider-balance proof or authorization to use that budget here.

These are live read-only search/API evidence, recorded execution replay, synthetic/perturbed fixtures, and mocked transport respectively. No new Jev inference, live UI check, provider timeout, or production rebuild was performed. A production integration would need a narrowly scoped reference assembler and fixed external rubric, deterministic source/receipt validity checks, a separately authorized bounded dispatcher, and task outcome measurement. That is more work than the current evidence justifies.

**Single best next action: do not add Jev to these development workflows now.**
