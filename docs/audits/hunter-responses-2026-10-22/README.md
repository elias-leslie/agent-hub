# Neri hunter response accounting

Agent Hub's existing Activity endpoint and page now include a compact **Neri hunter responses** disclosure. It uses only sessions explicitly assigned to Neri with the hunting or recon work role. This adds passive accounting to the existing service; it changes no hunting policy, recorder, target records, or lab behavior.

The former response-token evidence still describes normalized user turns. The new, separate `hunter_responses` evidence counts unique provider responses, so many Pi responses in one user turn remain distinct. It is never added to ledger totals.

## What the numbers mean

- A valid `scope=response` usage event needs a stable response ID and nonnegative integer input/output counts. The first retained valid usage event per session/response is counted once; later duplicates are counted as excluded. Thread/cumulative counters are not added. Invalid response usage is counted as unusable, with unknown missing size.
- Inclusive reported input and output remain separate. Cache read/write are subsets of inclusive input and never add again. Cache detail coverage shows the inclusive input with a valid cache split; uncovered input has an unknown split.
- Pi tool calls join only through the adapter's exact `message:<response_id>:<block index>` identity. User-turn IDs, nearby timestamps, call IDs and guessed intent never join a response. Other harnesses' response usage is retained but currently unknown for purpose. Unlinked calls are counted explicitly.
- The four categories are source/recon signal only (stable API enum `investigation_only`), mixed, support/coordination, and unknown. Both response share and inclusive-input-plus-output token share use the same retained response set. A mixed response stays whole; no tokens are divided between its tool calls. Capped event samples make all response categories unknown.
- The source/recon class is a conservative invocation signal: known source read/search tools or bounded shell forms pointing at configured source extensions/directories, plus the explicit Bugout recon-run prefix. It does not establish successful execution, a bug finding, exact token intent, or an accepted outcome. Instruction/document reads, unsupported shell syntax, opaque lab commands, and other unrecognized actions remain unknown. Source-like paths can still refer to support code; the classifier cannot establish target purpose from metadata.
- Per session, the first source/recon signal shows its action, linked sampled response number/input when available, and elapsed time since the first sampled provider response. Hub creation time is registration/import time, so it is not used to claim native startup delay. Response ordinals and first observations apply only to the selected window/sample; earlier work may be absent.
- First and peak input are **per response**. The cumulative input total includes repeated input across calls. Neither value proves resident context, compaction behavior or causal spend.

Classification choices live in the existing `activity_policy.json`. The output contains no prompt, tool body, command, path, search text, target content or provider-native usage body. Session/project/harness/work-role identities and numeric observations remain available for existing drill links.

## Live limits and manual baseline

At the first deployed API observation, the current explicitly Neri/hunting Codex session had 56 unique provider responses and all 56 were unknown for action purpose; 170 deduplicated calls lacked a response join. Its first/peak reported input was 20,931 → 157,088. A separate metadata-only linkage audit found 208 stored tool-use events under event-message or response-item identities, with no retained exact response IDs and zero exact identity matches to provider usage. Usage retains response and turn IDs, but tools do not retain the corresponding response identity. Future Codex attribution needs a separate explicitly coarser turn measure or a native-ingestion change. Timing and user turns must not become guessed response joins. These counts change as the live session continues.

The uncapped Pi query included five explicitly declared Neri sessions and 208 provider responses, with zero unlinked calls. The two older rows had 79/67 responses; their first/peak inputs were 6,119 → 137,381 and 5,421 → 119,028. Two newer hunting rows had 23/20 responses and no recognized source/recon signal. A recon row had 19 responses.

The broad metadata heuristic reported first source-like calls at sampled response 19/26 for the older pair, versus the coordinator's manual target-source review baseline of 23/19. The manual review described target inspection; this classifier observes configured source-like invocations, which can include support code and omit opaque calls. The two observations are deliberately distinct. The automatic view cannot identify when actual bug hunting began or allocate actual bug-work tokens. No exclusions were tuned to those sessions.
